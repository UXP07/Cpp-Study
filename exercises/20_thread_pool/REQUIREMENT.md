## 背景

16-19 的四块积木——thread 汇合（16）、mutex 守卫（17）、条件变量谓词
等待与优雅关停（18）、原子计数（19）——现在拼成一个真家伙：**线程池**。
生产者提交任务，一群常驻工人从队列取活干，关停时收完所有任务体面收工。
它是波次 9 事件驱动架构的发动机，也是"任务队列 + 条件变量 + 关停标志"
综合设计的标准考题。

**零输出**照旧；注释不要求；main 留空；判题端压测 + 关停语义核对
（挂起由外部 timeout 判死刑）。

## 需求

**Q1. class ThreadPool（唯一主角）**
- 构造 `ThreadPool(unsigned n)`：起 n 个工人线程，每个跑同一个 worker 循环
- `submit(std::function<void()> task)`：入队并唤醒一个工人；
  **已关停后 submit 抛 `std::runtime_error`**
- `shutdown()`：**优雅关停**——置关停标志、唤醒所有工人、join 全部；
  队列里的余货必须**全部执行完**才许收工（验收会专门压这条）
- 析构函数自动 shutdown（RAII——忘了手动关也不泄漏线程）
- worker 循环（设计核心）：**谓词等待"非空或已关停"**；取任务时持锁、
  **执行任务时不持锁**（锁粒度——17 号的纪律）

**Q2.（SR 主考）关停的两难与设计取舍**——见简答。

## 验收标准（判题端驱动核对）

- 基础压测：pool(4)，submit 10000 个"原子计数 +1"任务，shutdown 后
  计数 == 10000——**无任务丢失**，多轮运行稳定
- **带余货关停**：新池 submit 500 个任务后**立刻** shutdown——
  500 个必须全部执行完（优雅关停的核心验收）
- 关停后 submit 抛 runtime_error（驱动 catch 验证）
- 作用域析构路径：{ 池 + 任务，出作用域 } 不挂不漏（析构自动 shutdown）
- worker 的 wait 是谓词形式、执行任务时锁已放开（代码审查）
- 零输出零警告

## 简答题（答案写在 main.cpp 顶部注释块，白话作答）

SR1. 关停的两难：消费者（工人）醒来的谓词为什么必须是"非空 **或** 关停"？
     只等"非空"会怎样（shutdown 挂死在 wait 里）、只等"关停"会怎样
     （余货被丢）？你的 worker 拿到"关停且非空"时按什么顺序处理、
     为什么必须先清货再收工？
SR2. 执行任务时为什么必须放开锁？如果拿着队列锁执行任务，submit 端
     会发生什么（被堵多长——任务执行多久就堵多久）？这叫什么问题
     （锁粒度/持锁跨越昂贵操作）？
SR3. 压测里计数用的是原子 fetch_add 而不是 mutex——为什么这里 relaxed
     就够（19 号的账）？线程池的 submit 在高并发下的锁竞争是它第一个
     性能瓶颈——低延迟世界的解法方向是什么（预告波次 9：无锁队列/
     每工人独立队列）？
SR4. 你的线程池和"每任务一个线程"（16 号的裸 thread）比，省了什么
     （线程创建/销毁成本 + 上限可控）？什么时候池仍然不够好
     （任务极短、锁竞争主导——引出无锁）？
